# Offline Git delivery scenarios

Walk through the actual skill instructions with synthetic repositories, issue
records, and PR facts. Identify the next actions, the owning issue's audit entries,
the candidate, and the stopping point. Do not use live repositories or trackers;
these walkthroughs do not establish live permissions or successful merges.

| Scenario | Expected behavior |
| --- | --- |
| Intent gathering reaches a known migration repository and review expectations; no issue integration choice has been supplied. | Ask once between Issue PRs and Direct integration, explain the common gates and final destination PR, and record the answer in intent. If deferred, record Open and the resolution point without selecting a default. |
| Accepted intent selects Issue PRs; the repository permits them and two independent coding issues have passing checks. | Verify feasibility without asking again. Each issue branches from the migration branch, opens a PR into it, and integrates after its own gates. Each records its own PR, tested commit, and resulting parent commit. No destination PR is opened for this interim work. |
| Accepted intent selects Direct integration and required gates can be satisfied without an issue PR. | Verify feasibility without asking again. Prepare the candidate without moving the parent, satisfy the same checks, review, and acceptance, integrate into the verified parent, and record the approach and tested and resulting commits. Mark the issue PR not applicable, not missing. |
| A focused Transform invocation finds accepted intent leaves the choice Open, omits it, or selects Direct integration where branch protection requires issue PRs. | Transform pauses affected coding work and hands the intent reference, current choice, feasible approaches, and constraints to Initialize without editing intent. Initialize asks a person with decision authority, updates only the intent field, preserves any replaced choice and reason, saves and reads it back, and hands back the verified reference and value without opening a new intent issue or adding blockers. Transform rechecks feasibility before resuming its requested scope. |
| Initialize cannot save or read back the chosen issue integration approach. | Report the unfinished setup update; Transform keeps affected coding work paused and does not substitute a chat answer for the verified saved choice. |
| A proposed approach also changes another accepted requirement. | Follow the normal intent revision and acceptance procedure before affected work resumes. |
| A coding issue owns combined implementation and has a nested coding issue, which itself owns a required descendant. The phase aggregate is blocked on its slices. | Issue branches target their immediate integration parents under the selected approach. Integrate deepest work first; the parent waits for required descendants before integrating upward. Eligible issue integration proceeds without executing blocked aggregate checks or synthesis. Tracker hierarchy alone does not select a Git parent. |
| One issue used two branches and PRs: the first was retargeted, closed, and replaced, and its branch has been deleted. | Retain both entries on the issue with repository, original and current head/base identities, verified PR URLs, tested commits, disposition, reason and successor, and the resulting parent commit for the merged PR. Deleted refs remain auditable through names, PRs, and immutable commits. |
| An issue awaits required human PR review or slow CI, a parent has advanced, or integration access is unavailable. | Do not bypass the gate or claim integration. Pending issue gates alone do not trigger another choice. Reconcile a moved parent and refresh affected checks, review, and acceptance. Preserve audit facts, report the blocker, and continue independent eligible work. |
| Direct integration prepared a tested candidate, but the authoritative parent advanced or its remote update failed. | Do not overwrite the newer parent or mark the issue complete. Reconcile and refresh affected evidence when the parent moved; leave integration pending if the authoritative ref cannot be updated and confirmed. |
| A human marked a coding issue Done to accept its reviewed candidate, but its issue PR is still open. | Treat the acceptance as valid without treating the native status as Git integration. Reconcile the PR under repository gates and keep dependent code work from consuming it until it reaches the integration parent. |
| Resume an older migration with an existing stack, human-owned changes, and accepted evidence. | Reconcile actual state and the authoritative migration branch. Preserve existing issue and PR history, avoid destructive rewriting, and refresh only evidence affected by candidate or ancestry changes. |
| A repair is needed after the destination PR was opened, including when it was previously ready. | Transform integrates the repair issue under the accepted approach and refreshes the report and destination PR. Required verification becoming pending returns the destination PR to draft; the verifier checks the new exact candidate and links existing records. Old evidence remains historical. |
| All required migration implementation is integrated; final verification is pending, then passes for the current candidate. | At full-migration handoff open or reuse one draft migration-branch → destination-branch PR. The transform coordinator may mark it ready after applicable verification and repository gates; never merge it into the destination. A read-only status request reports the same links without changing state. |
| A tracker issue owns only coordination or verification, with no coding work. | Do not create a branch or PR solely to mirror the issue hierarchy. |
| Git is the bound provider and records are on its state branch. A code-only delivery is requested. | Keep issue audit records on the state branch and the migration integration branch distinct. Verify the outgoing history does not include record commits; use a verified record-free base for the code-only destination. |
