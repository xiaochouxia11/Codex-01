# Offline adapter scenarios

Use these synthetic scenarios to evaluate the actual skill instructions without
live integrations. Give an independent evaluator the user request, supplied facts,
and package path; let it load the entrypoint/references itself and return the next
reads/actions, copied handoff context, and stopping point. Do not give it the
acceptance column before its trace. Permit local reads only: no tracker tools,
record writes, installations, source execution, or real credentials.

These are behavioral walkthroughs of instructions, not proof of live permissions,
operation compatibility, publication, or parenting. Run package/link validation
and renderer checks separately. Live mutation tests need an explicitly agreed
test scope and disposable destination; never default to development examples.

Do not initiate implementation, grant acceptance, infer source parity, or generate a cross-skill continuation prompt. |

For a substantive change, also walk through a fully specified new migration until
the first record save/readback, using synthetic returned IDs/URLs. Check that a
new migration home exists before persisting its verified identity or linking
children, and that reports are created only when substantive content is available.

## GitHub Issues scenarios

Use synthetic host, repository, issue, and Project identities. CLI commands are
proposed actions only; do not run them against GitHub during an offline trace.

| User request and synthetic evidence | Acceptance checks after the trace |
| --- | --- |
| Start a new GitHub Issues migration without a Project. The integration can read and create issues; the confirmed records repository differs from the source repository. The home creation returns an issue ID/number/URL. | Bind the confirmed records repository, save and read back the returned home identity before creating dependent work, and create only the scope owned by initialize. No Project discovery, Git-provider state branch, or fabricated approval. |
| Add a migration's work to a selected existing Project. The integration exposes issue operations but no Project or hierarchy operations; authenticated CLI has the same authorized identity and can read both destinations. | Use the integration for supported operations and CLI only for gaps. Resolve Project owner/number/ID and field identities, add the home and owned work, verify native hierarchy, and keep issue state authoritative. No new Project, schema, or report items. |
| A required native blocker operation is missing from the integration; CLI is absent, uses a conflicting identity, or cannot access the bound repository. | Report the specific capability or identity gap and leave dependent work unstarted. Do not switch provider, bypass denied access, invent an operation, or change credentials. Independent work remains eligible. |
| Creating a home issue succeeds, but saving its returned identity fails; later, creating a work issue succeeds but attaching it to its parent fails. | Reuse and reread returned identities before retry. Do not create dependent records from an incomplete home binding or claim an unattached work issue is fully established; report exactly which step remains pending. |
| Accepted intent is revised. The integration lacks dependency operations; CLI exposes add/read but not removal. | Add and verify the new intent as a blocker of each affected unfinished consumer, in the correct direction, before replacing the old current intent. Name the exact old edge for manual removal and verify it before affected work proceeds; never infer a blocker from parenthood. |
| Request read-only status for a home with accepted work, an open report issue, an unrelated Project item, stale human-action labels, and an inventory capped at one page. | Exclude reports and unrelated items from work counts, suppress stale flags without edits, and qualify incomplete inventory rather than claiming completion. Read report timestamps from report issues; make no issue, Project, or repository changes. |
| A coding issue closes automatically when a PR merges, and its Project item says Done while required acceptance is still unresolved. | Treat the closure as a discrepancy, not approval; leave dependent work pending and avoid closing-keyword links for future work. Do not change records during a read-only request. |

### GitHub hierarchy capacity boundaries

Trace these cases using the GitHub adapter's capacity check before any issue
creation. These are offline acceptance scenarios, not live API validation.

| Synthetic evidence | Expected outcome |
| --- | --- |
| A new phase proposes 101 slices; its home has room for two phase parents. | Do not create the oversized breakdown. Replan into coherent phases with at most 100 total children each, preserve all 101 slices and their dependencies/verification obligations, check home and dependency capacity, and retain normal brief acceptance. With a tracked intent shared by all 101 slices, dependency capacity still fails: request a scope decision and do not create the revised breakdown. |
| A phase has 98 slices and one specialist; one repair is needed. | Complete enumeration gives 99 children; one repair fits as child 100. Save and verify its native parent and dependency relations. |
| A phase has 99 open children and one closed child; a new specialist or repair is needed. | Count 100, stop before creating child 101, record the blocker on the existing parent, and request authorized planning/reconciliation. Do not detach closed work, fabricate ancestry, or claim completion. |
| The home already has 100 direct children, or a child listing is incomplete. | Do not create another phase or standalone child. Report exhausted or unverified capacity respectively; preserve the one-home binding and leave dependent creation pending. |

### GitHub dependency capacity boundaries

Trace before creating work or adding dependencies; these offline scenarios do not
prove live API behavior.

| Synthetic evidence | Expected outcome |
| --- | --- |
| A tracked intent must block 51 technical items across two phases, each below 100 children. | Reject the proposed graph before creating its records. Report intent's outgoing capacity and require a scope decision; phase splitting and indirect blockers do not satisfy the policy. Repeat with applicable cloud setup as the saturated source. |
| Intent already blocks 49 distinct issues, including closed and unrelated work; one new consumer is proposed. | The 50th outgoing edge fits only if the consumer's incoming side also fits. An existing edge retried is counted once. |
| A consumer already has 50 incoming blockers but intent has outgoing room. | Stop before adding another blocker; check both endpoints and both directions independently. Do not remove existing requirements to make room. |
| A later repair needs intent/setup edges, an intent revision replaces a source, or relations change during a multi-edge write. | Recheck full capacity, preserve old required relations and saved IDs, reconcile partial writes by readback, and leave affected work pending until every required edge is verified. |

## Git scenarios

Use disposable local repositories for executable file/Git checks. Supply source,
review agreement, and repository facts explicitly; dummy remote URLs below are
fixtures, not proof of remote access. Snapshot tracked file contents, index, HEAD,
and refs before/after read-only status. Inspect the saved records and commit after
writing scenarios. Use only a disposable local bare repository to test publication;
never push to an external remote or contact a real tracker during these checks.

| --- | --- |
| Start a default workflow with Git explicitly selected, a clean migration repository and committed source, no tracker plugins, and a no-push instruction. Record file save and local commit as separate evidence, without claiming tracker or remote write access. After actual review and acceptance, continue requested checks whose own prerequisites are Done. |
| Run Workflow access with Git records available but missing CodeMod plugin files. The saved check contains its self-contained steps. | Use those steps to record the plugin gap and save/read back the real findings when possible.
